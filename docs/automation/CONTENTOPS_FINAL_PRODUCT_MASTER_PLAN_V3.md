# Capital Chronicle ContentOps — Final Product Master Plan V3

Authority date: 2026-08-19

## 0. Objective

Finish one coherent Capital Chronicle distribution-and-learning product without restarting historical hardening programs or building parallel authority stacks.

The final architecture is:

`Capital Chronicle/Core Analyzer intelligence and decision authority -> explicit publication-safe handoff + contextual discovery -> ContentOps intelligence fusion -> V1 publishing + V2 video/media -> observation -> bounded ContentOps learning -> audience/business utility`.

The immediate product problem is not lack of database discovery or lack of media infrastructure. It is that the strongest foundations are not yet connected end to end with enough **correctly classified upstream authority use**, source reachability, final live acceptance, and measurable audience/business feedback.

The product must optimize useful reader/business value while protecting the Core Analyzer final product. Internal decision, probability, scenario, forecast, regime, paper, and outcome-attribution outputs are not ContentOps publication inputs by default.

## 1. Verified foundation inventory

Current repository foundation already provides:

- read-only discovery of the local Capital Chronicle DuckDB estate;
- schema/table profiling and catalog fingerprinting;
- deterministic schema-relevance ranking;
- story-scoped context queries;
- governed surface inspection;
- a read-only bridge to Capital Chronicle publication evidence;
- a separate read-only bridge to the Analyzer closed-loop point-in-time handoff;
- exact permission/freshness/lineage validation for publication packets;
- claim-level evidence/permission objects with point-in-time fields;
- explicit `llm_numeric_authority=false` contracts;
- current V1 bounded editorial context fields for CC context and chart inputs;
- at least one V2 path that consumes publication-authorized numeric claims, packet provenance, and time-series/chart inputs.

The code currently distinguishes three materially different upstream states:

1. arbitrary CC database context, which returns `grants_factual_or_numeric_authority=false`;
2. the governed Analyzer closed-loop handoff, which can be internally validated and point-in-time but remains candidate/context and publication-blocked unless a separate public contract grants use;
3. the story-scoped `CapitalChroniclePublicationEvidencePacketV1.json` path, which may authorize exact ContentOps public use only when consumer, story authority, public permissions, source health/freshness, blockers, and validation all pass.

This distinction is product-critical. The word `governed` does not mean `public`.

Recent current canary evidence also discovered 14 CC stores and 176 candidate tables per candidate, yet representative ranked stories still queried zero tables because semantic entities/topics were empty. This proves a contextual activation gap, but **database query volume is diagnostic evidence, not the product objective**.

## 3. Final architecture and authority boundaries

### 3.1 Capital Chronicle/Core Analyzer intelligence and decision authority

Capital Chronicle/Core Analyzer remains authoritative for proprietary calculations, numeric truth, scenarios, probabilities, forecasts, regimes, analytical conclusions, prospective scoring, decision briefs, private decision/watch/abstain outputs, paper expressions, realized outcomes, and analytical error attribution.

ContentOps is read-only toward that authority. No ContentOps model, heuristic, chart renderer, or adapter may create missing CC numeric truth or widen an internal artifact into public authority.

### 3.2 Upstream publication-safe handoff

Public ContentOps use of proprietary CC/Core Analyzer material must pass through an explicit story-scoped publication contract.

The current canonical example is:

`docs/research/publication_evidence/current/CapitalChroniclePublicationEvidencePacketV1.json`.

An explicit compatible successor is allowed, but it must preserve the same essential safety properties:

- intended ContentOps consumer/use explicitly granted;
- exact story binding/scope;
- explicit public claim/reporting permission;
- claim/series/calculation identity;
- exact `known_at`/`as_of`/observation/revision semantics where relevant;
- lineage/provenance and source references;
- DQR/source-health/freshness state appropriate to the scoped claim;
- blockers/limitations;
- no hidden global-authority upgrade;
- `llm_numeric_authority=false`.

A global DQR block may coexist with a narrowly authorized story packet. ContentOps must preserve the exact upstream scope, not convert local authorization into global clearance.

### 3.3 Context/discovery

Read-only CC database querying exists to improve investigation, history, entity/event understanding, source discovery, and editorial questions.

Context-only material can help answer “what should we investigate?” or “what prior state matters?” It cannot answer “what proprietary number may we publish?” without independent accepted evidence or a publication-authorized upstream packet.

### 3.4 ContentOps intelligence fusion

For each credible current candidate, the fusion layer should combine:

- current headline/event discovery;
- latest accessible public evidence;
- published-memory/update-chain context;
- relevant read-only CC context/discovery;
- exact publication-authorized CC/Core Analyzer packets where applicable;
- rights-safe visual/data opportunities;
- current portfolio/performance signals that affect priority/packaging only.

### 3.5 V1 publishing

One canonical V1 runtime owns newsroom state, article/package production coordination, publication, readback/reconciliation, observation scheduling, and recovery. No parallel newsroom/store/publisher is authorized.

### 3.6 V2 media

V2 is a downstream isolated factory. It never creates or mutates V1 publication/runtime authority. It consumes a qualified story package and may consume proprietary numeric/chart material only through the same publication-authorized upstream boundary.

### 3.7 Observation and bounded learning

Observation records what actually happened. Learning proposes bounded changes to ContentOps priority, timing, packaging, SEO, hooks, assets, and creative policy. It never changes Core Analyzer factual/numeric/decision authority.

## 4. P0-1 — Core Analyzer publication-authority utilization + CC context activation + source reachability

This is the first implementation capability after this authority correction.

### 4.1 Product problem

The current system has two different under-use problems that must not be conflated:

**A. Publication-safe upstream intelligence is not first-class enough in story qualification.** ContentOps must explicitly detect whether a current story has an exact publication-authorized CC/Core Analyzer packet, consume it when relevant, and truthfully record why it was absent/rejected/unused.

**B. Contextual database enrichment is underactivated.** Current production evidence can show:

`14 stores discovered -> 176 candidate tables -> 8 schema-relevant tables ranked -> 0 tables actually queried`.

The principal observed cause is weak/empty story semantics (`entities_topics=[]`) before story-scoped query execution. A newer rehearsal path has a fallback, but the main preselection path still directly queries from `entities_topics`.

Fix both in one vertical slice without allowing B to masquerade as A.

### 4.2 Upstream publication-authority resolver

Before proprietary CC/Core Analyzer content is used publicly, resolve the exact upstream state:

1. publication-safe packet present and compatible;
2. exact story/consumer binding matches;
3. permissions allow the intended ContentOps use;
4. claim/series/calculation lineage and point-in-time state are intact;
5. source health/freshness/blockers pass for the scoped use;
6. output may be projected to V1/V2 without value regeneration.

Otherwise classify precisely, for example:

- `NO_PUBLICATION_AUTHORIZED_CC_PACKET_FOR_STORY`;
- `CC_PUBLICATION_PACKET_STORY_BINDING_MISMATCH`;
- `CC_PUBLICATION_PACKET_PERMISSION_BLOCKED`;
- `CC_PUBLICATION_PACKET_STALE_OR_SOURCE_UNHEALTHY`;
- `CC_GOVERNED_SURFACE_COMPATIBILITY_REQUIRED`;
- `CC_INTERNAL_ANALYZER_HANDOFF_NOT_PUBLICATION_AUTHORITY`;
- `CC_CANDIDATE_ONLY_NOT_PUBLICATION_AUTHORITY`.

Do not synthesize a replacement value.

### 4.3 Semantic activation for context

Before bounded context querying, each candidate should deterministically or safely derive a normalized query context where evidence supports it:

- entities and institutions;
- countries/regions;
- sectors/industries;
- asset classes/instruments;
- economic concepts/data releases;
- event/policy type;
- historical-comparison questions;
- transmission/cross-asset questions.

The semantic activator does not grant factual authority. It only creates query intent. Preserve the exact source fields from which semantics were derived.

If meaningful semantics truly cannot be established, record a zero-use reason rather than forcing a query.

### 4.4 Bounded relevant context querying

Reuse current estate discovery and deterministic schema ranking. Do not query everything.

Recommended behavior:

1. refresh/fingerprint current estate;
2. rank relevant candidate tables from current schema;
3. select a bounded number of tables based on story semantics and schema compatibility;
4. execute read-only story-scoped queries;
5. return compact matched context and quality/freshness metadata;
6. record exactly why a selected table was or was not queried/matched.

Querying more tables is not success. The success condition is useful relevant context with bounded cost and zero authority promotion.

### 4.5 Point-in-time, lineage, DQR, degradation, and schema compatibility

Preserve where available:

- `known_at`;
- `as_of`;
- source/event/observation/revision times;
- estate/catalog/schema fingerprint;
- packet, source, series, calculation, model/run identity;
- evidence refs and citations;
- DQR/source-health/freshness;
- permission state;
- observed/forecast/scenario classification;
- candidate/proxy/degraded/blocked state;
- exact limitations/forbidden use.

A stale/incompatible governed surface should return a bounded compatibility blocker, not silently fall back to internal numeric truth and not veto an unrelated ordinary factual article.

### 4.6 Shared publication-authorized chart/data projection

Implement one safe V1/V2 chart-data contract instead of a separate V2 analytical store or a new ContentOps analytical authority layer.

The ContentOps packet must be a lossless projection of an upstream publication-authorized packet.

Minimum fields:

- upstream packet ID/hash and exact story/consumer binding;
- chart/series/calculation IDs;
- `known_at`, `as_of`, observation/source/revision time;
- observed vs forecast vs scenario state;
- units and transformation;
- values or safe display projection;
- provenance/evidence refs;
- DQR/freshness/source health;
- rights/reuse/public-display permission where relevant;
- blockers/limitations;
- schema/version/fingerprint;
- `llm_numeric_authority=false`.

V1 may use it for article charts and explicit publication-safe analytical context. V2 may use the same packet for analytical maps, charts, timelines, and visual evidence. Neither lane may repair missing values, infer permissions, or convert an internal Analyzer handoff into public authority.

### 4.7 Utilization telemetry

Persist compact per-candidate/per-run telemetry that separates authority classes:

**Upstream publication-safe use**
- publication-authorized packets discovered;
- exact story-bound packet selected;
- authorized claim/series/chart counts available;
- authorized claim/series/chart counts actually consumed;
- rejected packet reason and exact blocker;
- upstream packet ID/hash/authority class.

**Context use**
- CC estate/catalog fingerprint;
- stores/tables discovered as diagnostics;
- ranked/selected tables;
- actual queried tables;
- matched stores/tables;
- match count/context richness;
- semantic activation inputs/output;
- zero-context-use reason;
- read-only/upstream-mutation proof;
- query elapsed time/budget.

The UI must eventually answer two separate questions:

1. “What publication-authorized Capital Chronicle/Core Analyzer intelligence did this story actually use, and under what exact permission?”
2. “What additional CC context did ContentOps consult for investigation, and why?”

### 4.8 Acceptance

A real zero-write vertical slice should cover at least four distinct current story classes and prove:

- at least one story with an available exact publication-authorized upstream packet consumes that packet end to end without value regeneration;
- a governed Analyzer/internal handoff that lacks publication permission remains non-public even if validated and point-in-time;
- candidate/proxy/degraded/stale/incompatible upstream states remain visible and blocked for unsupported use;
- relevant stories produce meaningful context query intent and actually query bounded tables when justified;
- irrelevant stories may correctly use zero CC context;
- database query volume is never used as a success metric;
- one publication-authorized chart/data projection is consumable by both V1 and V2 adapters;
- latest-web public evidence can coexist with and complement CC authority without being replaced by it;
- no upstream mutation and no model-created numeric substitution;
- telemetry truthfully explains every upstream/context zero-use case.

## 5. Latest-web evidence/source resolver

### 5.1 Problem

Recent canaries show source acquisition failing due to unavailable embedded URLs, missing publish timestamps, insufficient bound source bytes, and request-budget exhaustion.

### 5.2 Direction

For each high-ranked candidate, prefer:

`candidate -> current locator/search/research -> accessible primary source -> strong accessible professional secondary where needed -> normalized exact source record -> evidence packet`.

Do not treat the discovery URL embedded in an X/feed item as the only possible evidence route.

No login/paywall/anti-bot bypass. Never upgrade snippets/model summaries into source authority.

### 5.3 Acceptance

- accessible primary sources are preferred when known;
- bounded secondary recovery is available when primary delivery is unavailable and policy permits;
- source identity, URL, publish/known time, content hash, authority class, and permission are preserved;
- blocked source delivery is distinguished from an unverifiable story;
- request budgets are candidate-aware so one brittle source does not exhaust the whole publishability walk;
- minimum trustworthy evidence remains fail-closed.

## 6. V1 final acceptance

After P0-1 is corrected, run one fresh canonical V1 live acceptance path.

Required sequence:

1. recover/reconcile any prior obligations;
2. ingest current headlines and build the real current candidate universe;
3. resolve current publication-authorized CC/Core Analyzer material plus bounded context and latest-web evidence;
4. rank/qualify and abstain if no story is strong enough;
5. when a qualified article exists, invoke exactly the current owner-authorized editorial worker boundary;
6. deterministic factual/numeric/rights/reader-value validation;
7. purposeful article media, including zero images when preferable;
8. verify exact readiness for Substack plus all eight V1 derivative destinations;
9. canonical Substack-first publication;
10. attempt every required derivative under exact destination identity;
11. read back/reconcile every public object;
12. require `UNKNOWN_WRITE=0` and no ambiguous pending reconciliation;
13. schedule supported observations;
14. Jim/ChatGPT inspect the actual public article and derivative artifacts.

A legitimate `NO_PUBLICATION` proves safe abstention but is not final publication canary proof.

After an accepted real canary, enable only the already-authorized current four V1 tasks and prove unattended/cold-start operation before `V1_FINAL_PRODUCT_ACCEPTED`.

## 8. V2 final creative factory and soak

Continue from the current accepted creative-authority architecture rather than rebuilding it.

Canonical flow:

`qualified governed story -> publication-authorized analytical/chart inputs where available -> institutional analytical map -> evidence expansion -> visual entity/asset needs -> fresh rights-safe asset board -> visual-fit selection -> story-specific free-form Remotion source -> short + justified longform -> professional audio -> final-audio-bound transcript/package -> deterministic hard-boundary QA -> actual-media XHIGH/owner review -> bounded localized repair -> owner master`.

Key acceptance:

- viewer-facing source remains story-specific rather than fixed-template substitution;
- concrete evidence/assets dominate over generic abstract visuals;
- proprietary charts/data are publication-authorized upstream projections and remain legible, with full-chart holds when the whole chart matters;
- no private Analyzer output is converted into documentary/public chart authority;
- asset-family repetition is controlled qualitatively, not by file-count quotas;
- picture/audio caching and localized repairs work without unnecessary full rerenders;
- repeated unattended jobs recover safely;
- actual media is owner-accepted;
- measured TCO/runtime stays bounded;
- no video public write.

## 9. V1 -> V2 qualification loop

Do not produce a video for every article.

A shadow scorer should combine only supported signals:

- real V1 story usefulness/performance;
- evidence and publication-safe analytical depth;
- visual/rights-safe asset supply;
- narrative shelf life;
- portfolio novelty/repetition;
- expected production cost/time.

Output: `QUALIFIED`, `DEFERRED`, or `ABSTAIN`, with reason codes. Engagement may change priority but cannot create evidence, CC publication permission, or Core Analyzer authority.

## 10. Publication/readback beyond V1

Any future V2 platform publication must be separately owner-authorized by exact destination/account, public-object type, visibility, provider/browser boundary, recovery policy, and readback contract.

No provider adapter or credential existence is publication authority.

A successful future write counts only after exact public-object identity/content readback and reconciliation. Unknown result always stops retries until readback.

## 11. Retention attribution and video learning

After a real eligible public cohort exists, collect supported platform-native metrics such as completion, retention curve, rewatch, share, save, click/subscriber effects where APIs/authorized observation permit.

Bind metrics to exact media/package/public-object identity and scene/beat ranges where trustworthy. Learning may suggest hook, pacing, asset, chapter, package, or qualification changes. It cannot rewrite past factual evidence, upstream CC/Core Analyzer outputs, probabilities, scenarios, forecasts, decisions, or publication permissions.

## 12. Closed ContentOps learning and business funnel

Long-term observation should connect content identity to supported acquisition/conversion outcomes:

`article/video -> landing/signup -> returning user -> beta/product use -> paid -> retained`.

Do not overfit small samples. Low-confidence learning should produce no-op or bounded recommendations.

ContentOps may use observed audience value to request new analysis or alter editorial priority/packaging. It may not feed engagement directly into Core Analyzer numeric truth, model probability, forecast, regime, decision, paper, or realized-outcome records.

The business objective is lower cost and higher quality of acquiring, educating, converting, and retaining Capital Chronicle users — not maximizing content volume, database utilization, or automation ceremony.

## 14. Anti-overengineering and exact deferrals

Do not build before direct product need:

- a second CC database or broad mirror;
- query-all-table behavior;
- a ContentOps clone of the Core Analyzer;
- a separate V2 analytical engine;
- a ContentOps service that recalculates private Core Analyzer probabilities/scenarios/forecasts for publication;
- automatic exposure of decision briefs, private watch/abstain outputs, paper positions, model internals, or realized-outcome records;
- a new newsroom/store/publisher/scheduler authority;
- broad multi-agent role expansion;
- arbitrary model bakeoffs;
- a second dashboard/control plane;
- deterministic aesthetic quotas pretending to equal quality;
- full historical backfills unrelated to current story utility;
- broker/live execution;
- video public-write expansion before exact owner grant;
- autonomous public replies/DMs;
- broad security/compliance ceremony not tied to a real product blocker.

Prefer one implementation, one independent audit, and at most one bounded correction.
